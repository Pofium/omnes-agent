# BACKEND_SPEC.md — Архитектурная спецификация бэкенда OmnesAgent (Rust Workspace)

Настоящий документ определяет целевую архитектуру, структуру крейтов, принципы разделения ответственности, контракты данных, политики безопасности и подсистемы локального инференса бэкенда OmnesAgent.

---

## 1. Обзор архитектуры и принципы проектирования

Бэкенд OmnesAgent спроектирован как высокопроизводительный, модульный монорепозиторий на языке **Rust** (MSRV 1.80+ / 1.96+) с асинхронным рантаймом **Tokio**.

### Ключевые архитектурные принципы:
1. **Single Source of Truth:** Бэкенд является единственным владельцем состояния системы, выполнения команд ОС, хранения долговременной памяти и маршрутизации LLM.
2. **Zero Unhandled Panics:** Все пути выполнения в production-коде должны корректно распространять ошибки через `anyhow::Result` или типизированные ошибки доменных крейтов без паник.
3. **Безопасность и Human-in-the-Loop:** Ни одна потенциально деструктивная операция (модификация защищенных файлов, запуск команд с высоким риском, доступ к внешним сетям) не выполняется автоматически без прохождения через `approval_gate`.
4. **Graceful Degradation:** Отсутствие локальных весов нейросетей, сбои внешних API или перегрузка сети никогда не приводят к аварийной остановке системы.

## 3. Сетевой шлюз (`omnesagent-gateway`)

Шлюз обеспечивает взаимодействие с Flutter Desktop/Web клиентами по протоколам HTTP/1.1, HTTP/2 и WebSocket.

### 3.1. Service Discovery
- [x] При запуске шлюз автоматически связывается с адресом `127.0.0.1:0` (динамический порт, если порт по умолчанию 42617 занят) и атомарно записывает файл дескриптора в `.omnes/gateway.json`:
```json
{
  "pid": 12840,
  "port": 42617,
  "host": "127.0.0.1",
  "started_at": "2026-09-20T22:30:00Z"
}
```

### 3.2. REST API Маршруты
- [x] `GET /health` / `GET /api/health` — проверка доступности шлюза.
- [x] `GET /api/v1/sessions` — список активных и архивных сессий.
- [x] `POST /api/v1/sessions` — создание новой сессии (с привязкой к проекту и ветке).
- [x] `GET /api/v1/providers` — реестр доступных провайдеров моделей (облачные + локальные Ollama/LM Studio).
- [x] `POST /api/v1/ast/reindex` — триггер фоновой переиндексации AST-графа кодовой базы.
- [x] `GET /api/v1/s1/status` — текущий статус слоя System One (готовность весов, используемый провайдер).
- [x] `POST /api/v1/s1/download` — команда на фоновую предзагрузку весов модели Laya.
- [ ] `GET /api/v1/editor/tree` — дерево файлов проекта (ленивая подгрузка уровней, git-статусы узлов).
- [x] `GET /api/v1/editor/file` / `PUT /api/v1/editor/file` — чтение файла в буфер и атомарная запись (temp + rename). *(Ф0; PUT защищает грязный буфер — 409 без `force`.)*
- [x] `GET /api/v1/editor/buffers` / `DELETE /api/v1/editor/buffer` — реестр открытых буферов (путь, ревизия, грязный флаг, EOL, кодировка, `read_only`) и закрытие буфера. *(Ф0: кодировка — utf-8; полный набор кодировок — Ф3.)*
- [x] `GET /api/v1/editor/raw` — сырые байты файла проекта (превью изображений и бинарных ассетов): канонизация пути, проверка рабочего корня, лимит 64 МБ, `Content-Type` по расширению, буфер не создаётся. *(Ф0, вьюер изображений правой панели.)*
- [ ] `GET /api/v1/editor/symbols` — символы файла (outline) из AST/LSP.
- [ ] `GET /api/v1/editor/find` / `GET /api/v1/editor/search` — поиск в файле и по проекту (regex, case, whole word), по проекту — потоково.
- [ ] `GET /api/v1/editor/git/diff` — ханки диффа против HEAD/индекса.
- [ ] `POST /api/v1/editor/git/stage-hunks` / `unstage-hunks` / `revert-hunks` — операции по диапазонам буфера (в терминах якорей, не текста файла).

### 3.3. WebSocket Диспетчер
Обрабатывает постоянное соединение клиента, транслируя:
- [x] Потоковые чанки генерации ответа LLM (`agent_chunk`).
- [x] Запросы подтверждения опасных действий через Human-in-the-Loop (`approval_request` / `approval_response`).
- [x] События прерывания речи (`voice_barge_in`) для немедленной остановки TTS и генерации.
- [x] Информационные метрики производительности и задержки (S1 Latency, Token Usage).
- [x] **Отдельный канал редактора `/ws/editor/{buffer_id}`** — постоянное соединение на каждый открытый буфер (открытие, дельты строк, правки, курсоры, фолды, диагностики, LSP-запросы, предложения агента). Формат фреймов и инварианты — §9.9. Канал `/ws/chat` остаётся каналом диалога и наблюдаемости и не несёт потоковых данных редактора. *(Ф0: hello / rows_request+rows_snapshot / rows_changed / edit_ops+edit_ack / save+save_state / error; фолды, диагностики, LSP, agent_proposal — Ф1/Ф5/Ф7.)*

## 4. Локальный нейро-слой System One (`omnesagent-s1`)

Слой System One (S1) на базе модели **Laya** (`convaiinnovations/laya`, ModernBERT-large + Decision Head, 421M параметров) предназначен для сверхбыстрого выполнения атомарных оценочных решений без обращения к удаленным LLM.

### 4.1. Контракт данных
- [x] **`Question`**:
  - `Choice`: выбор одной из категориальных опций (`id`, `prompt`, `options`).
  - `Score`: шкала оценки от 1 до N (`id`, `prompt`, `max_score`).
  - `Noul`: калиброванная семантическая вероятность истинности утверждения 0.0..1.0 (`id`, `prompt`).
- [x] **`Answer`**:
  - Строго типизированный результат с валидированными аксессорами `noul_prob()`, `choice_value()`, `score_level()`.

### 4.2. Провайдеры и автозагрузка весов
- [x] **`NoOpSystemOne` (`provider: off`):** Выключен по умолчанию. Нулевые накладные расходы.
- [x] **`FakeSystemOne` (`provider: fake`):** Детерминированные ответы для тестов.
- [x] **`CandleLayaProvider` (`provider: candle`):**
  - Реализован на базе `candle-transformers 0.8` и `tokenizers 0.21`.
  - **Автоматическое разрешение весов:** При отсутствии локального пути `OMNESAGENT_S1_PATH` использует `hf-hub` для проверки стандартного кэша `~/.cache/huggingface/hub/`. Если файлы отсутствуют — автоматически скачивает `config.json`, `tokenizer.json`, `model.safetensors` (~800 МБ) с Hugging Face Hub.
  - **Head+Tail Truncation:** При превышении лимита токенов сохраняет начальный контекст и конец реплики.
  - **Изоляция в потоке:** Инференс выполняется в `tokio::task::spawn_blocking` с ограничением по тайм-ауту (`OMNESAGENT_S1_TIMEOUT_MS`, по умолчанию 150 мс).

### 4.3. Точки интеграции в рантайм:
- [x] 1. **Быстрый Gate каналов (`omnesagent-channels`):** фильтрация спама и определение необходимости ответа в групповых чатах за ~30 мс.
- [x] 2. **Семантическая компактификация (`omnesagent-runtime/agent/history_trim.rs`):** функция `trim_with_s1_scoring` оценивает ценность реплик диалога (1..5) по отношению к цели и удаляет низкоприоритетные витки для экономии токенов.
- [x] 3. **Rerank памяти (`omnesagent-runtime/agent/memory_inject.rs`):** фильтрация кандидатов долговременной памяти по калиброванной Noul-вероятности (порог 0.40).
- [x] 4. **Шлюз инструментов (`omnesagent-runtime/agent/context_analyzer.rs`):** мультиязычная подсказка требуемых категорий инструментов.
- [x] 5. **Семантический роутер (`omnesagent-runtime/agent/classifier.rs`):** классификация запросов пользователей по профилям `fast`, `code`, `reasoning`.

## 5. Граф знаний кода и KAG (`omnesagent-kag`)

Обеспечивает глубокое структурное понимание кодовой базы проекта без расхода токенов внешних LLM.

- [x] **AST-парсеры:** Поддержка 10 языков (Rust, Python, TypeScript/JavaScript, Go, Dart/Flutter, PHP, Java, SQL, C/C++). Извлечение символов (`fn`, `struct`, `class`, `trait`, `interface`) и ребер (`CALLS`, `IMPORTS`, `DEFINES`, `INHERITS`).
- [x] **Графовая аналитика:**
  - Расчет **PageRank** для выявления ключевых архитектурных узлов (**God Nodes**).
  - Алгоритм Тарьяна (SCC) для поиска циклических зависимостей.
  - Метрики нестабильности компонентов ($I = C_e / (C_a + C_e)$).
  - Расчет **Blast Radius** (радиуса поражения) перед внесением правок в код с градацией риска `Low`, `Medium`, `High`.
- [x] **Векторный движок:**
  - Встроенный Candle BERT MiniLM (`all-MiniLM-L6-v2`, 384 dim) на CPU.
  - Алгоритм ранжирования **Reciprocal Rank Fusion (RRF $k=60$)** для объединения полнотекстового поиска FTS5 и векторного сходства.

## 6. Память и хранилище (`omnesagent-memory`)

- [x] **Хранилище:** Встроенная SQLite с FTS5 и поддержкой векторных блобов.
- [x] **Временное затухание:** Экспоненциальное затухание релевантности старых воспоминаний (Half-life 30 дней).
- [x] **Дедупликация:** MMR (Maximal Marginal Relevance) с коэффициентом $\lambda = 0.7$ для предотвращения дублирования однотипных фактов в системном промпте.
- [x] **Изоляция сессий:** Разделение памяти на уровни `Global` (профиль и привычки пользователя), `Project` (архитектурные решения) и `Session` (краткосрочный диалоговый контекст).

## 7. Безопасность и Approval Gate (`omnesagent-tools`)

Все действия инструментов категоризируются по уровням риска:
- [x] **Low (Read-only):** Чтение файлов, поиск по коду, проверка git status, HTTP GET запросы — выполняются автономно.
- [x] **Medium (Idempotent Writes):** Редактирование локальных файлов в рамках проекта, создание временных скриптов — логируются с возможностью отката.
- [x] **High (Destructive & System):** Выполнение shell-команд (`rm`, `git push --force`, запуск системных процессов, модификация системных файлов вне репозитория) — **обязательно блокируются** до получения явного подтверждения пользователя через `ApprovalRequestFrame`.
- [x] **Правило защиты S1:** Никакие вероятностные выводы модели Laya не имеют права переопределять или обходить `approval_gate`.

## 8. Бэкенд-подсистема расширенной наблюдаемости, траекторий и диалогового UX

Для обеспечения требований фронтенда по адаптации возможностей **DeepSeek Harness** и оптимизации диалогового взаимодействия (устранение расхождений, структурирование CoT, трассировка) в бэкенде реализуются следующие подсистемы.

### 8.1. Потоковая диспетчеризация траекторий (Trajectory Streaming Engine)
- [x] **Таблица `session_steps` в SQLite `sessions.db`:**
  ```sql
  CREATE TABLE IF NOT EXISTS session_steps (
      id TEXT PRIMARY KEY,
      session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
      turn_id TEXT NOT NULL,
      step_index INTEGER NOT NULL,
      parent_step_id TEXT,
      step_type TEXT NOT NULL, -- 's1_gate', 'context_inject', 'cot_thinking', 'tool_call', 'tool_observation', 'synthesis'
      payload_json TEXT NOT NULL,
      tokens_used INTEGER DEFAULT 0,
      duration_us INTEGER DEFAULT 0,
      created_at TEXT NOT NULL
  );
  CREATE INDEX IF NOT EXISTS idx_steps_session_turn ON session_steps(session_id, turn_id);
  ```
- [x] **WebSocket фрейм `trajectory_step`:** шлюз отправляет атомарные события траектории клиенту в реальном времени, позволяя строить интерактивный граф исполнения шагов.

### 8.2. Движок ветвления сессий (Session Forking & Time Travel)
- [x] **REST-эндпоинт `POST /api/v1/sessions/{id}/fork`:**
  - **Входные параметры:**
    ```json
    {
      "at_step_id": "step_abc123",
      "new_title": "Оптимизация (Ветка 2)",
      "overrides": {
        "model": "deepseek-r1",
        "system_prompt": "...",
        "mode": "deep_code"
      }
    }
    ```
  - **Логика бэкенда:** Атомарно создает новую сессию, копируя историю сообщений и шагов ровно до момента `at_step_id`. Состояние файлов и памяти изолируется в отдельную ветвь диалога.

### 8.3. Анализатор и профилировщик бюджета токенов (Context Budget Profiler)
В `omnesagent-runtime/src/agent/context_budget.rs` реализуется динамический замер токенов перед каждым вызовом LLM:
- [x] Подсчет компонентов:
  - `system_tokens`: базовый системный промпт и схемы тулов.
  - `kag_ast_tokens`: внедренные фрагменты графа кода и сигнатуры.
  - `memory_tokens`: факты долговременной памяти после MMR-фильтрации.
  - `dialog_history_tokens`: сжатая история реплик.
  - `tool_outputs_tokens`: выводы завершенных инструментов текущего витка.
  - `compression_saved_tokens`: объем сэкономленных токенов благодаря `omnesagent-compression` (Zstandard / SQZ) и семантическому триммингу `omnesagent-s1`.
- [x] Регулярная отправка фрейма `context_budget_update` на клиент.

### 8.4. Двухканальный стриминг рассуждений и цитирований (DeepSeek CoT & Grounding)
Для устранения расхождений в диалогах и разделения рассуждений от полезного ответа шлюз разделяет стриминг на специализированные фреймы:
- [x] **`thinking_chunk`:** поток скрытых рассуждений модели (`<think>` CoT от DeepSeek-R1 / Claude Thinking), передаваемый в изолированный канал для отображения в сворачиваемом блоке.
- [x] **`answer_chunk`:** основной полезный текст ответа (алиас к `agent_chunk` / `chunk`).
- [x] **`grounding_citation`:** структурированные ссылки на источники фактов (путь к файлу `repo/src/auth.rs#L40`, id узла AST-графа или ключ долговременной памяти). Клиент рендерит их как кликабельные интерактивные бейджи с номерами, исключая субъективные домыслы модели.

### 8.5. Профили операционных режимов (Execution Profiles Engine)
Рантайм поддерживает динамическое переключение профилей исполнения (`AgentExecutionMode`):
- [x] **`Fast`:** приоритет локального S1 (Laya), жесткое сжатие контекста, легкие модели (DeepSeek-V3), температура 0.2.
- [x] **`DeepCode`:** максимальная глубина KAG (3 уровня зависимостей), авто-запуск проверок компилятора (`cargo check`, `flutter analyze`).
- [x] **`Architect`:** увеличенный бюджет CoT-рассуждений (DeepSeek-R1), двухфазная верификация, обязательная генерация артефактов планов.
- [x] **`RalphLoop`:** автономный цикл до 10 итераций с автоматической проверкой тестов и откатом изменений при регрессии.

### 8.6. Экспорт и воспроизведение трасс (Trace Replay & Eval API)
- [x] **`GET /api/v1/sessions/{id}/export_trace`:** выгрузка сессии в стандартизированный формат JSONL (по стандарту `omnesagent-eval`), содержащий точные системные промпты, входные данные, вызовы инструментов и вердикты.
- [x] **`POST /api/v1/sessions/replay`:** запуск детерминированного воспроизведения трассы для оценки качества обновленных моделей и отладки регрессий.

## 9. Ядро редактора файлов (File Editor Core)

Раздел нормативный. Определяет разделение ответственности между шлюзом и клиентом, модель текста и правок, слои представления, интеграцию с LSP, файловой системой, git и агентскими инструментами. План внедрения по фазам — в `PLAN_FILE_EDITOR_ZED.md` (корень репозитория).

### 9.1. Принцип владения: единственный буфер

- [ ] **Шлюз — единственный владелец буферов файлов проекта.** Клиент (Flutter Desktop/Web) **никогда** не читает и не пишет файлы проекта напрямую: ни `dart:io`, ни `universal_io`, ни обход дерева каталогов. Всё — через `/api/v1/editor/*` и `/ws/editor/{buffer_id}`. Это распространяет принцип §1 «Single Source of Truth» на редактор. *(Ф0: владелец буферов в шлюзе работает (`EditorService`), вкладка `editor` не касается диска; окончательное выключение старых путей чтения — Ф3.)*
- [ ] **Миграция техдолга (обязательна):** существующие пути прямого доступа к ФС из клиента подлежат удалению — `frontend/desktop/lib/features/workspace/task_workspace_controller.dart` (`openProjectFile` → `universal_io.File(...).readAsStringSync()`), `frontend/desktop/lib/widgets/desktop_sidebar.dart` (обход ФС через `universal_io.FileSystemEntity.isDirectorySync`). Дерево проекта и содержимое файлов приходят из `GET /api/v1/editor/tree` и `GET /api/v1/editor/file`.
- [ ] **Реплики правок.** Каждая правка имеет автора-реплику: `0` — ядро шлюза (системные операции, автосохранение, форматирование), `1` — UI-окно пользователя, `2..N` — агентные сессии/инструменты, `1024+` — удалённые клиенты (web/телефон). Undo-стек разделён по репликам: `Ctrl+Z` пользователя не отменяет принятые правки агента, и наоборот. *(Ф0 частично: undo-стек клиента держит только свои правки (инвариант §9.9.4), явные replica-id во фреймах — Ф7.)*
- [x] **Буфер — объект, а не файл.** Один буфер на путь (реестр буферов), состояние: ревизия, грязный флаг, EOL, кодировка, `read_only`, язык. Сохранение — отдельное явное действие; правки живут в памяти до записи. *(Ф0: `EditorService` — реестр с ключом по каноническому пути, повторное открытие возвращает тот же buffer_id; кодировки помимо utf-8 — Ф3.)*

### 9.2. Модель текста и правок (`omnesagent-editor`)

- [x] **Хранение текста:** rope с дельтами (`xi-rope`-модель: `Rope`, `RopeDelta`, `DeltaBuilder`, `Transformer`, `Interval`, `Spans`). Трансформация позиций относительно дельты (`Transformer`) — базовый механизм переноса курсоров, диагностик и декораций при правках. *(Ф0: `lapce-xi-rope 0.4.0` + вендор `floem-editor-core` @ `1351ffb1` (MIT, `omnesagent-editor/vendor/`); явный `Transformer`-перенос декораций — Ф5/Ф7.)*
- [x] **Модель правок:** ревизии буфера, группы undo (правки группируются: автоиндент откатывается вместе с переведённой строкой), «живые» и отменённые группы, tombstones. Оптимистичное применение правок с проверкой ревизии: правка применяется, только если её базовая ревизия совпадает с текущей (`base_rev + 1 == rev`), иначе клиент получает корректировку (`edit_ack.adjusted_ops`) или `remote_ops`. *(Ф0: rev-гейтинг `base_rev == rev` на шлюзе, одна правка-фрейм = одна ревизия = одна undo-группа floem; расхождение → `edit_ack {applied:false}` + идемпотентный resync; `adjusted_ops`/реплики — Ф7.)*
- [ ] **Якоря для долгоживущих позиций** (комментарии ревью, ханки диффа, закладки): тонкий слой поверх `Transformer` — позиция, переживающая цепочку независимых правок. Кратковременные позиции (курсоры, подсветка поиска, диагностики) хранятся как смещения с трансформацией по дельте.
- [x] **Инварианты буфера** проверяются в тестах и под `debug_assertions`: корректность ревизий (монотонность), согласованность undo/redo (round-trip), состояние «грязный/чистый» относительно последней записи на диск. *(Ф0: 27 тестов `omnesagent-editor` — rev-гейтинг, undo round-trip, кириллица/эмодзи/CRLF-координаты, атомарное сохранение, доступ по корням; randomized-фаззинг — Ф2.)*
- [x] **Вендоренные подкрейты** в `omnesagent-editor/vendor/` с фиксацией ревизии upstream в `THIRD_PARTY.md`: модель редактора (`editor-core`: буфер, undo, курсоры, выделения, слова, отступы, режимы, регистры, команды, графемный `char_buffer` для IME) и суммирующее дерево (`sum_tree`). *(Ф0: `vendor/editor-core` @ floem `1351ffb1` — 9102 строки, байт-в-байт, лицензия MIT, упаковка описана в `VENDOR_NOTES.md`; `sum_tree` осознанно отложен — он нужен только при переходе на Zed-модель display-map (§11.12), Ф1+.*

### 9.3. Слои представления и render plan

- [ ] **Координатные пространства** и их строгая типизация (источник массовых багов при самодельной реализации): байты (`Offset`) ↔ строки/колонки (`Point`) ↔ UTF-16 (`PointUtf16`, для LSP) ↔ позиция после развёртки табов (`TabPoint`) ↔ после переноса строк (`WrapPoint`) ↔ после фолдов (`FoldPoint`) ↔ после инлайнов (`InlayPoint`) ↔ рисуемая строка (`DisplayRow`/`DisplayPoint`).
- [ ] **Слои представления** (каждый со своим контрактом «что на входе → что на выходе» и инкрементальным пересчётом только затронутых областей): табы, перенос строк (`none` / `editor_width` / `bounded`), фолды (по отступам/скобкам и LSP `foldingRange`), инлайны (inlay hints, призрак-предложение агента), блоки (inline-виджеты: предложения агента, комментарии ревью), подсветка диапазонов (поиск, правки агента, диагностики).
- [ ] **Render plan** — то, что уходит клиенту вместо текста файла: для каждой видимой display-строки — `row`, `buffer_row`, `kind` (text/fold/block/spacer), `text` (с развёрнутыми табами), `runs` (run-length: длина + id стиля), `inlays`, `fold` (скрытые строки, метка), `indent_guide_cols`, `selections`. Таблица стилей (`style_id → {color, bg, underline, bold, italic, strikethrough}`) отправляется один раз на сессию и при смене темы.
- [x] **Дельта вместо полного кадра.** Правка порождает перечень инвалидированных строк (`start_line`, `inval_count`, `new_count`, старый текст) — клиент перезапрашивает только их. Полный `rows_snapshot` по диапазону идемпотентен и служит «лечением» после рассинхронизации. *(Ф0: `InvalLines` floem → фрейм `rows_changed` с готовыми строками диапазона (без round-trip), `rows_snapshot` идемпотентен; `old_text` для клиентских конфликтов — Ф7.)*
- [ ] Клиент получает только видимый диапазон + шаг предзагрузки; память вьюпорта — `O(видимых строк)`, независимо от размера файла. *(Ф0 частично: рисуется только видимое окно; клиент кэширует весь документ — окна строк + prefetch приходят в Ф1.)*

### 9.6. Файловая система, сохранение и конфликты

- [ ] **Наблюдение за ФС** (`notify`): события создания/изменения/удаления/переименования, подписка на открытые буферы и корень проекта; ошибки запуска watcher'а логируются, не паникуют.
- [ ] **Атомарная запись:** temp-файл в том же каталоге + `rename`, сохранение прав/атрибутов; поддержка `create_parents`; бэкап перед перезаписью — существующий механизм `omnesagent-tools/backup_tool.rs`. *(Ф0: temp + rename в `save()` и `PUT /api/v1/editor/file`, `create_parents` в PUT; сохранение атрибутов и подключение backup_tool — Ф3.)*
- [ ] **Конфликты:** если файл изменён на диске, а буфер грязный — клиенту уходит `save_state` с описанием дрейфа; UI предлагает «перечитать / оставить моё / показать разницу». Молчаливая перезапись запрещена.
- [ ] **Очистка при сохранении:** удаление trailing whitespace и гарантия финального перевода строки — по настройкам (`remove_trailing_whitespace_on_save`, `ensure_final_newline_on_save`).
- [ ] **EOL и кодировка:** определение при чтении (LF/CRLF/CR, UTF-8/UTF-8 BOM/UTF-16/legacy через `encoding_rs`), сохранение в исходном виде по умолчанию; отображение в статус-баре.
- [ ] **Большие и не-текстовые файлы:** порог (≥ 10 МБ) и бинарные файлы — предупреждение и режим «plain/read-only» вместо редактора с подсветкой.
- [ ] **Защита путей:** те же правила, что в §7 (запрещённые каталоги, `read_only` для файлов вне рабочего корня, проверка на симлинки при записи).

### 9.7. Интеграция с агентом (общий буфер вместо «запиши файл»)

- [ ] **Инструменты агента работают через буфер.** `omnesagent-tools/file_edit.rs`, `file_write.rs` и правки по патчам переводятся на API буфера: открыть буфер → применить правки как транзакцию с репликой агента → пометить буфер грязным (запись на диск — по политике: сразу либо через подтверждение `approval_gate`). Прямая запись файла в обход буфера допускается только как fallback с обязательной инвалидацией буфера.
- [ ] **Предложения вместо перезаписи (`agent_proposal`).** Правка агента может быть доставлена как набор ханков: клиент показывает inline-виджет с «принять/отклонить» (по ханку, файлу, всем), принятие применяет правки с репликой агента. Отклонение не меняет буфер.
- [ ] **Совместная работа без потери правок.** Правки человека и агента применяются к одному буферу через модель ревизий/дельт; при конфликте (правка на основе устаревшей ревизии) выполняется слияние либо возврат клиенту с корректировкой.
- [ ] **Присутствие и следование (`presence`).** Клиент видит, где сейчас работает агент (диапазон, метка сессии), и может включить «следовать за агентом» (автоскролл к текущей правке).
- [ ] **Правки агента — часть траектории.** Применение правок агентом порождает шаг траектории (§8.1, `tool_call`/`tool_observation`) со ссылкой на диапазон в буфере, что связывает наблюдаемость и историю файла.
- [ ] **Откат правок агента:** история правок с фильтром по реплике — «отменить все правки этой сессии агента в файле».

### 9.8. Интеграция с git

- [ ] **Дифф против базы:** база — HEAD (или индекс) содержимое файла; пересчёт ханков по дельтам буфера (не повторный запуск `git diff` на каждую правку).
- [ ] **Гуттер-маркеры:** добавленные/изменённые/удалённые строки и блоки, ховер ханка, переход к предыдущему/следующему ханку.
- [ ] **Операции по ханкам:** `stage` / `unstage` / `revert` ханка по диапазону буфера (в терминах якорей), с корректной работой при последующих правках; результат проверяется `git status`/`git diff --cached`.
- [ ] **Статусы в дереве:** изменённые/новые/удалённые/переименованные файлы рабочего дерева; ветка и счётчики изменений.
- [ ] **Blame** (опционально, настройкой): инлайн-подпись коммита на текущей строке.
- [ ] Не допускается выполнение деструктивных git-операций без `approval_gate` (§7).

### 9.9. Протокол канала редактора

**REST** — список в §3.2 (`/api/v1/editor/*`). Все изменяющие операции идемпотентны там, где это возможно, и возвращают новую ревизию буфера.

**WebSocket** `/ws/editor/{buffer_id}` — фреймы (команды: клиент→шлюз; события: шлюз→клиент):

| Фрейм | Направление | Назначение |
|---|---|---|
| `hello` | S→C | Буфер, язык, ревизии, EOL/кодировка, `read_only`, таблица стилей, настройки редактора |
| `rows_snapshot` | S→C | Диапазон display-строк (инициализация, скролл, лечение после сбоя) |
| `rows_changed` | S→C | Инвалидированные строки после правки (дельта) |
| `edit_ops` | C→S | Правки клиента (оптимистично применённые локально), с `base_rev` и id реплики |
| `edit_ack` | S→C | Подтверждение/корректировка правки по ревизии |
| `remote_ops` | S→C | Правки других реплик (агент, другое окно) с автором |
| `cursor` / `selection` | C→S | Позиции/выделения клиента (якоря) |
| `presence` | S→C | Где работает другая реплика (агент) |
| `folds` | C→S | Операции фолдов (свернуть/развернуть/всё) |
| `diagnostics` | S→C | Диагностики файла (диапазоны в UTF-16, severity, source) |
| `lsp_request` / `lsp_response` | C↔S | Запросы LSP-фич (completion, hover, definition, code_action, format, signature, inlay_hints) |
| `server_status` / `work_done_progress` | S→C | Состояние языковых серверов и прогресс длительных операций |
| `agent_proposal` / `agent_proposal_result` | S↔C | Предложение правок агента и решение пользователя (принять/отклонить по ханкам) |
| `save_state` | S→C | Грязный флаг, факт сохранения, дрейф файла на диске |
| `show_message` / `log_message` | S→C | Сообщения LSP-серверов для UI |
| `error` | S→C | Ошибка с кодом и контекстом |

Инварианты протокола (обязательные):
1. Каждый фрейм несёт ревизию буфера (для строк — ревизию представления); фрейм с несовпадающей базой не применяется.
2. Команды идут только в одну сторону (клиент командующий, шлюз — источник событий); назад приходят только подтверждения/корректировки.
3. `rows_snapshot` идемпотентен для диапазона — позволяет восстановиться после потери фреймов без перезагрузки буфера.
4. Правки, пришедшие от других реплик, никогда не попадают в локальный undo-стек клиента.
5. Авторизация канала — те же правила, что для остальных WS-каналов (токен дескриптора шлюза), с проверкой, что затребованный буфер входит в разрешённый рабочий корень.

### 9.10. Конфигурация и приёмка

- [ ] **Секция `[editor]` в `config.toml`** (+ переопределения по языку `[editor.languages.<lang>]`): `tab_size`, `hard_tabs`, `soft_wrap`, `preferred_line_length`, `autosave`, `format_on_save`, `remove_trailing_whitespace_on_save`, `ensure_final_newline_on_save`, `show_whitespaces`, `relative_line_numbers`, `scroll_beyond_last_line`, `cursor_blink`, `multi_cursor_modifier`, `lsp_highlight_debounce`, `diagnostics_max_severity`, `minimap`, `vim_mode` (по умолчанию выключено). Настройки применяются без перезапуска шлюза.
- [ ] **Бюджеты производительности (приёмка):** открытие файла 1 МБ < 300 мс до первой отрисованной строки; ввод символа до кадра < 16 мс (p99 < 33 мс); пересчёт подсветки после правки < 8 мс на файлах до 5k строк; скролл в файле 100k строк без просадок ниже 55 fps; память шлюза на буфер 1 МБ < 20 МБ (текст + история + кэш подсветки).
- [ ] **Обязательные тесты:** инварианты буфера и randomized-правки (свойство: результат совпадает при любом порядке независимых правок); round-trip «правка → undo → redo»; стабильность якорей; конвертеры координат (туда-обратно) на кириллице/эмодзи/CRLF; дельта → LSP `TextDocumentContentChangeEvent`; git-ханки против `git diff`; два клиента на одном буфере (человек + агент) без потери правок; LSP — против реального сервера и фейкового (JSON-RPC по stdio).
- [ ] **Функциональный минимум (Definition of Done) для подсистемы:** открыть/изменить/сохранить файл из правой панели; подсветка не менее Dart, Rust, JSON, YAML, TOML, Markdown, Shell; gutter-диффы и `stage` ханка; диагностики и автодополнение при доступном языковом сервере; одновременное редактирование человеком и агентом без потери правок; ни одного прямого чтения/записи файлов проекта из Flutter.
